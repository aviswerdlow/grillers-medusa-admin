## Customer and staff behavior

The active payment step shows a server-derived review before placement: items and quantities, fixed/per-pound price basis, estimated food weight and total, shipping, tax/discounts included, billing and delivery addresses, receipt email/phone, actual service/date/window, approved invoice terms or card consent, and canonical legal links. Direct edit links return to the existing cart, address, date and profile screens. Changes and expiry disable placement until refreshed. The separate legacy review component is not the integration point.

Customer card checkout keeps the existing save-card/charge-when-packed flow. Approved invoice checkout needs the account's actual terms; there is no Net 10 fallback. Staff immediate collection needs verified `collect_card_now` authority and consent. It refuses catch-weight lines: use the existing customer final-charge checkout or send-checkout-link path instead of charging an estimate as a fixed final payment. Native Admin direct/draft order creation and conversion are denied, including for operators, because they bypass the accepted review.

An uncertain response is not a reason to collect another payment. Customer status recovery can replay only an already completed cart with its original review/request identifiers. Staff keep their confirmed payment reference and expose a completion-only retry. This is source behavior, not yet a native/provider recovery receipt. Browser reload persistence and every recovery scenario must be checked in the integrated rehearsal.

## API and authority

`POST /store/carts/:id/order-review` accepts only `action: review | accept | recover`, `payment_mode: card | card_at_placement | invoice`, a UUID `request_id`, optional `review_id`, and nullable boolean `analytics_consent`. The browser cannot submit a promise, price, ListID, terms document, receipt destination or test flag. `recover` refuses an uncompleted cart before calling native completion.

`POST /store/grillers/checkout/place-order` requires the review and request identifiers for customer saved-card or approved invoice placement. `POST /store/carts/:id/complete` is the reviewed staff immediate-payment adapter, carrying identifiers in `x-gp-order-review-id` and `x-gp-order-request-id`; native SDK body validation remains intact. It retains the native result envelope.

The authenticated customer must own the cart. Staff authority comes only from the existing middleware-verified signed cart/customer handoff and current staff session. The trusted adapter rechecks the actor's capability, session epoch and access generation at native copy. Staff browser analytics consent is stored as unknown, never attributed to the customer. The public review allowlist omits accounting IDs, internal packing/costs, private receipt IDs and experiment data. Public cart responses redact the server-owned snapshot pointer.

## Trusted data and timing

`src/lib/order-review-checkout.ts` derives the full promise from the exact cart the native workflow copies, current server catalog records, an owned immutable receipt snapshot, accepted calendar and shipping contracts, and published sale terms. Cart-line injections cannot supply pricing mode, food weight, name or QBD ListID. It stamps the accepted server values onto copied line metadata. RM items, absent identity/pricing/contact/terms and changed inputs fail closed. Explicit zero totals remain zero. Pie-space allowances never become food charge weights.

The Strapi published Terms of Sale query matches the storefront legal source fields. Its document and SHA-256 revision are archived. This establishes the source revision, not Peter/Avi's legal approval or proof that every editorial block was rendered. Fetching is bounded to five seconds; an unavailable or incomplete source blocks a new review. A read-only diagnostic returned the expected published source after the original two-second loader failed. The failure's exact cause was not proven; candidate availability and latency remain rehearsal gates. No CMS write occurred.

Semantic comparison omits changing capture/acceptance timestamps and decrypts the signed shipping price instead of comparing randomized ciphertext. All four fulfillment modes are preserved; regional pickup includes the configured city/state. Reviews expire at the earliest of 15 minutes, calendar quote/cutoff, signed shipping-token expiry and shipping-policy validity. Unknown experiment versions, analytics consent and Stripe mode remain null; they are not verified measurement data.

## Lock, completion and original evidence

Review issue/acceptance, metadata stamps and shipping-heal writes use the same cart-ID lock key as native Medusa cart mutation/completion. Native completion acquires that lock itself; do not invoke native cart workflows inside a review lock callback. The existing single `completeCartWorkflow.hooks.validate` callback composes receipt, calendar, shipping and review validation against the actual native copy source. It does not register a second competing hook. Actual native stock/reservation atomicity remains #312/#364 work.

`src/lib/order-promise.ts` and the catch-weight migration own three append-only tables: issued reviews, accepted snapshots and successful native order bindings. Acceptance compares the normalized promise, records a monotonic revision and updates the cart pointer transactionally. Replays retain the original expiry; an idempotency key cannot change meaning or revive a superseded acceptance. Database triggers reject UPDATE/DELETE. Historical orders are not backfilled from current state.

`completeReviewedCart` keeps the real in-process `completeCartWorkflow.run()` return. `bindOrderPromise` requires the matching `complete-cart` transaction/input, successful done state, order/run IDs, durable completed cart/order/link, owner and matching pointers. An order ID, client success flag or event payload is insufficient. It then initializes packing from the bound original. A binding/finalization interruption returns an explicit recovery error without initiating another provider action. Replaying a completed cart uses its original acceptance, not current profile/catalog data.

The existing order-placed packing subscriber defers a reviewed order until binding exists. `acceptedFinalizationSource` maps the native order-line IDs to immutable accepted cart lines and uses original identities, food-pricing basis and placement totals. Changed quantity/product/variant/line membership requires the unfinished amendment workflow. Legacy orders retain their old path. Packing's later actual weight/final charge remains distinct from the original placement estimate.

Medusa 2.10.3 queues `order.placed` before its final authorization steps and clears grouped events during compensation. This source observation does **not** show failed orders escaping as events. Only a real integrated rehearsal can establish native event/recovery ordering. Stripe, Medusa, allocation, bridge, QBD and messages each require their own receipt.
