# Accepted-order evidence — #368 source contract

Tracking: [strategy #368](https://github.com/aviswerdlow/grillers-pride-strategy/issues/368). This candidate introduces the internal evidence ledger and its transaction boundary. It does **not** complete #368: the customer review UI, trusted cart adapter, native completion wiring, staff amendments, QBD corrections and runtime acceptance remain required. No route, subscriber or current checkout consumes this ledger yet. Do not close the issue or deploy this as a completed checkout feature.

## What the ledger guarantees

`src/lib/order-promise.ts` and the catch-weight migration own three append-only tables: issued reviews, accepted snapshots and successful native order bindings. An acceptance records the reviewed customer/contact/address/line/price/calendar/packing/terms/attribution data. Amounts are USD major units rounded to cents. The placement amount is an **estimate accepted at placement**, not a paid amount or the later final charge.

Reviews expire in at most 15 minutes; the checkout adapter must further cap expiry at every applicable signed quote/cutoff. A retry returns the original expiry. Acceptance locks the owned cart, compares the entire normalized promise, inserts a monotonic revision and updates the cart pointer in the same transaction. A changed request cannot reuse an idempotency key, and replay cannot revive a superseded acceptance. Database triggers reject UPDATE/DELETE of evidence. No historical orders are backfilled with today's totals or contact information.

`validateOrderPromiseSnapshot` is a pre-creation check. It requires the current owner, current snapshot pointer, unexpired review and the same promise. It must be used in the existing single `completeCartWorkflow.hooks.validate` callback against the **exact cart object that native Medusa copies**. A separate hook would replace/conflict with receipt, calendar and shipping checks. Completed-order retries must use the previously bound original, not reconstruct a review from current catalog/profile data.

`bindOrderPromise(db, cartId, completion)` accepts the actual in-process return from `completeCartWorkflow.run()`. It requires `complete-cart`, the matching transaction/input cart, a finished `done` state without errors, and the order/run IDs. Recovered transactions may supply their original input through `getContext().payload`. It then verifies the durable native order, completed cart, live order/cart link, customer ownership and matching snapshot pointers before writing one immutable binding. A client success flag, order ID or event payload is insufficient. A new completion run returning the same order does not replace the first binding.

The installed Medusa 2.10.3 workflow queues `order.placed` before payment authorization and its final steps; `emitEventStep` groups events and clears grouped events during compensation. This source observation is **not evidence that failed orders currently escape as events**. The ledger nevertheless requires an explicit successful workflow return. Native lifecycle/recovery behavior must still be proven in the integrated rehearsal, and provider payment, accounting and allocation evidence remain separate.

`readOriginalOrderPromise` requires a binding and a live native order/link with the original customer. It never substitutes current totals. `orderPromiseAnalytics` returns an allowlist: stable order ID, accepted revision/time, native placement time, original estimate/currency/unit/basis, calendar/review revisions, experiment assignments, consent and test marker. It excludes addresses, emails, phones, lines, accounting IDs and payment instruments. This helper does not send an event, claim payment success, or override downstream consent. #335/#336 must use it only through an authorized reader and the agreed lifecycle event matrix.

The `gp_order_promise_` metadata namespace is server-owned in the existing customer/staff cart authority guard. Customer/staff requests cannot inject the pointer through public cart writes.

## Required next integration, in dependency order

1. **Trusted review adapter and UI — #368, #331/#362/#365/#366.** Derive the promise from server-owned cart/catalog data, verified receipt selection, accepted shipping/calendar/packing contracts and approved terms. Never accept the full promise, amount, ListID, terms, test flag or receipt email from the browser. Use stable semantic values: omit changing `captured_at`/`acceptedAt` timestamps from comparison and decrypt the accepted shipping contract rather than hashing randomized ciphertext. Preserve the actual four calendar modes. Treat weights as physical/food/space inputs according to #361; never use Peter's pie-space proxy as food weight. Display the exact reviewed addresses, arrival/window/service, lines, quantities, price basis, estimate, shipping policy and contact with direct edit links. Missing/unapproved input blocks review; no invented invoice terms or operating defaults.
2. **Native checkout and stock composition — #312/#314/#318/#320/#329/#359/#364.** Carry only the review/request identifiers from the UI. Serialize review acceptance, cart mutation and native completion with a common cart lock; the short SQL acceptance lock alone does not prevent a later cart change. Revalidate at native copy, bind only the successful workflow return and reconcile a post-completion binding failure without creating a second order. Keep native customer completion, saved-card, invoice, staff and draft-order paths from bypassing the review/authority gate. Keep actual incoming reservations and native allocation atomic/recoverable. This candidate does not resolve the stopped #312 fixture.
3. **Original-evidence consumers — #335/#336/#367/#369.** Publish a dedicated authorized read contract; preserve server-side idempotent placement and later finalization events with one stable order ID. A missing original is unavailable, never zero/current/final amount. Don’t use a full private snapshot as an event, log, generic customer API response or operations alert.
4. **Staff correction workflow — #368/#359/#370.** Peter's whitelist, cutoff and approval policy remain unanswered. Build explicit consequence preview and revision/capability/reason/approval checks. Append a separately audited correction; do not mutate the original. Fresh calendar, incoming stock, tax, promotions, final-charge/invoice exposure and picking races must be checked together. After cutoff, use the approved cancellation/replacement exception path. Profile edits cannot redirect an existing order.
5. **QuickBooks and rollout — #314/#317/#320/#368.** `update_sales_order_items` is not a certified bridge operation. Verify TxnID/EditSequence and the approved correction mapping before enabling amendments. Retain the immutable outbox and separate Stripe/Medusa/bridge/QBD receipts. Apply the migration only in the authorized integrated candidate/rehearsal. Rollback keeps evidence tables; any retention/purge/recovery procedure needs separate review. Do not drop accepted history as an automatic rollback.

## Verification boundary

Focused unit tests check normalization, required amounts/terms/dates, privacy projection, completion receipts and public pointer injection. The PostgreSQL suite runs the actual ledger migration and transactions in an explicitly isolated local database, testing concurrency, staleness, rollback, ownership/link forgery, append-only storage and original amount/contact retention. Its narrow cart/order/link tables and controlled workflow return fixture **do not execute native Medusa completion or provider calls**. CI also runs the inherited accounting, receipt and incoming-stock suites plus TypeScript. Native/provider acceptance and all original #368 criteria remain open.

For an isolated local PostgreSQL instance use `ORDER_PROMISE_TEST_DATABASE_URL` pointing to loopback database `gp_order_promises` (CI uses `gp_launch`), or `ORDER_PROMISE_TEST_PG_SOCKET` for port 55468/user `gp_order_promise_test`. Run `TEST_TYPE=integration:order-promise yarn jest --runInBand`. The suite never reads `DATABASE_URL`.

No customer/staff operating behavior is enabled by this internal contract, so the staff operations guide is unchanged. Update its checkout review and order-correction instructions with the consuming UI/native adapter; do not describe planned behavior as available.
