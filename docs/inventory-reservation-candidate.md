# Native reservation candidate for strategy #312 — verification

This draft stacks on #340 and preserves the existing staff-authority and public-catalog contracts. It does not write production stock. Peter's approved physical/QBD stock export, location and exception dispositions are still required for a separate baseline operation.

The candidate removes the unmanaged/backorder `999999` assumption and cached-QBD fallback. It uses mapped native inventory levels and refuses missing baselines. It compares advisory allocations to native reservation rows by line, item and location, so mirrored demand is not deducted twice. Availability reads only allocations for variants linked to the cart's inventory components, retaining shared-item checks. The existing future-dated ordering window remains available; #364 will add confirmed-incoming quantity limits. Order-row locking makes advisory placement and whole-order release replay-safe. Native cart/payment guards refuse unverified stock only when `GP_NATIVE_INVENTORY_CHECKOUT_ENABLED=true`; the default is off.

Medusa 2.10.3's reserve-step rollback hard-deletes reservation rows and leaves `inventory_level.reserved_quantity` occupied. A version-pinned postinstall correction uses Medusa's counter-safe soft-delete method in that one compensation handler, and the native fixture checks both the row and counter after rollback. The actual cancel-order step releases by line item. Explicit pre-fulfillment refund quantities release the same line's native reservation and advisory allocation, keyed for replay safety. CI runs these against a disposable PostgreSQL database and independent Redis clients, including last-unit concurrency.

Do not activate native checkout guards or apply a production stock baseline from this candidate. Peter's export and a separate reviewed baseline operation remain prerequisites. Stripe refund success alone is not inventory release; only a validated pre-fulfillment line-quantity refund invokes the release path.
